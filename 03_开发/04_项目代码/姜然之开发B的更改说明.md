# 开发B的更改说明

> 本文说明开发B在开发A交接版本（`杜梦涵开发A/`）基础上做的更新，以及运行于 `http://127.0.0.1:8000` 的新版本相对开发A的优势。
>
> 开发A版本：Flask + BM25 本地关键词检索，端口 `5000`，仅后端接口。
> 开发B版本：Python 标准库 + 阿里云百炼语义检索（RAG），端口 `8000`，带完整前端页面与简短回答。
>
> **注：第一至六节为第一轮（RAG 语义检索）记录；测试阶段发现 RAG 在实时/未知类问题、QM 编号过载、路径泄露与索引管理方面存在问题，第七节记录了据此将检索内核调整为「本地结构化索引」的修复，当前运行版本以第七节为准。**

---

## 一、概述

开发A完成的第一轮成果是「本地关键词检索后端」：先用 `parse_pdf.py` 把 200 页 PDF 解析成 `knowledge_base.json`，再用 jieba 分词 + BM25 做关键词匹配，`app.py` 只提供 `/api/search` 接口、没有前端页面，并把「信息不足判断」「前端」等留给开发B。

开发B接手后做了两处方向性调整，并补齐了前端与交付：

1. **检索内核从“本地关键词匹配”换成“云端语义检索”**：直接调用阿里云百炼知识库（`index_id: 6xchq9wqwz`）的 RAG 检索接口，不再需要本地解析 PDF、维护 JSON、建 BM25 索引。
2. **补齐完整前端网站与“简短回答”**：新增 `index.html / static/style.css / static/app.js`，并把「简短回答 + 检索依据」作为页面的核心展示方式。

## 三、逐项更新说明

### 3.1 检索方式：关键词(BM25) → 语义(RAG)

- **开发A**：jieba 分词后做 BM25 词法匹配，只能命中「字面相同」的词语。用户说「刚从冰箱拿出来能不能马上倒热水」，若资料原文是「冷藏后先恢复室温、注意温差」，BM25 难以靠词面关联命中。
- **开发B**：改为调用阿里云百炼知识库的语义检索接口（`POST /api/v1/indices/rag/index/retrieve`，`index_id=6xchq9wqwz`），按向量相似度召回，对口语化、同义改写的问题更友好。

**优势**：从「词面匹配」升级为「语义匹配」，召回的片段更贴合用户真实问法。

### 3.2 依赖：约 20 个第三方库 → 零依赖

- **开发A**：`requirements.txt` 含 Flask、flask-cors、rank-bm25、jieba、pymupdf、onnxruntime、numpy 等约 20 个包，安装耗时且 onnxruntime 等体积较大。
- **开发B**：后端只用 `http.server` + `urllib` 两个标准库模块，`python app.py` 即可运行，**无需 pip install**。

**优势**：开箱即用，规避依赖冲突与环境搭建问题，便于教师快速验收。

### 3.3 前端：无 → 完整网站

- **开发A**：只有后端接口，注释写明「允许跨域，方便开发B写前端」。
- **开发B**：补齐 `index.html`、`static/style.css`、`static/app.js`，实现搜索框、快捷示例按钮、`Ctrl+Enter` 提交、加载态、简短回答卡片、结果卡片（含 QM 编号、页码、相关度、内容、来源）、错误/低相关提示。

**优势**：从「接口」变成「可演示、可交互的完整知识库网站」。

### 3.4 简短回答：无 → 有

- **开发A**：只返回 top5 原文块，客服需自己通读筛选。
- **开发B**：新增 `build_short_answer()`，从检索片段中抽取资料自带的「客服答复示例 / 处理说明 / 处理要点 / 保温性能 / 使用方法 / 规格与价格」字段，按「问题类型 + 型号命中 + 关键词命中」打分，选出最相关的一段，页面顶部先行展示，下方再列出检索依据。

**优势**：客服一眼看到可直接回复的话术，缩短响应时间；回答来自资料字段、非模型编造，满足「回答有依据」。

### 3.5 查询扩展

- **开发B** 新增 `expand_query()`：识别型号（GB-400 / BX-500 / BH-1000）及中文叫法（保温杯、保温壶、玻璃杯），并追加领域关键词（保温性能、温差、裂纹、漏水、清洗、售后、物流等）后再检索。

**优势**：实测三条客户示例问题（冷藏倒热水、保温时长、裂纹处理）均能命中正确条目。

### 3.6 信息不足判断：TODO → 已实现

- **开发A**：留了注释「检查最高分（可选）……给开发B留出空间」。
- **开发B**：已实现——无结果或最高相关度低于 `LOW_CONFIDENCE_THRESHOLD`（默认 0.30）时返回 `insufficient=true`，前端提示「资料可能未覆盖，请向用户补充信息，不要编造」。

**优势**：落实客户「资料不足时不编造」的要求。

### 3.7 封面/目录过滤

- **开发B** 新增 `_is_toc_only()`：只过滤不含任何正文字段（常见问题、处理说明、客服答复示例等）的纯封面/目录切片，保留「封面+正文」合并的切片，避免误删有效内容。

**优势**：减少目录页噪声，提升结果可用性。

### 3.8 配置与密钥管理

- **开发B** 把 `DASHSCOPE_API_KEY`、`DASHSCOPE_INDEX_ID` 等放到 `.env`（已 `.gitignore`），并提供 `.env.example` 模板；`app.py` 从环境变量 / `.env` 读取，密钥不写死。

**优势**：符合作业「不要提交真实密钥」的要求。

### 3.9 代码质量

- **开发A** 的 `app.py` 把两份几乎相同的代码拼在一起（重复定义 `app`、`search`）。
- **开发B** 重构为单文件、函数化：`expand_query / parse_nodes / build_short_answer / _handle_search` 等，职责清晰、无重复。

**优势**：更易维护、可解释、便于核对代码贡献。

### 3.10 端口与访问

- 开发A：`0.0.0.0:5000`；开发B：`0.0.0.0:8000`（均满足局域网访问要求，监听所有 IPv4 接口）。

## 四、优势总结

1. **检索更准**：语义 RAG 取代关键词 BM25，口语化问题召回更稳定。
2. **更易运行**：零第三方依赖，`python app.py` 一键启动，无需先解析 PDF、无需装 20 个包。
3. **可直接使用**：补齐前端页面与「简短回答 + 检索依据」展示，从接口升级为完整产品。
4. **更符合客户要求**：信息不足不编造、回答有依据、可回到原文核对。
5. **更规范的交付**：密钥用 `.env` 管理、代码无重复、运行说明完整。

## 六、已知限制与待办

- 「简短回答」为规则抽取（非大模型生成），依赖检索排序；未指定型号的个别问题（如「如何清洗」）可能取到相近而非精确条目，客服仍需结合下方检索内容核对。
- 检索质量受教师所建知识库的切片策略影响（切片会合并多个主题）。
- 后续可评估：接入百炼「知识问答」接口生成总结式回答、增加原文高亮定位、补充自动化回归测试。

## 七、测试问题修复记录（对应《02_问题跟踪与复测》）

针对测试阶段记录的 7 个缺陷，本轮做了如下修复：

| 问题 | 级别 | 修复内容 |
| --- | --- | --- |
| BUG-01 | 阻断 | 新增 `detect_unanswerable()`：对实时订单/物流状态、实时库存、未记录功能（App/蓝牙/Wi-Fi/温度曲线）做规则拦截，明确返回「无法确认」及核验指引，不再当有依据作答。 |
| BUG-02 | 高 | 检索改为本地结构化索引（219 个 QM 主题），按「型号 + 意图 + 字段内容锚点」加权排序；简短回答按意图抽取对应标准字段，避免复用少数固定话术、与问题错配。 |
| BUG-03 | 高 | 每条结果改为单一 QM 编号、真实页码、随条「资料版本 2026-10」字段；过滤封面/目录页；不再展示 OSS `file_path`；相关内容条数动态统计（不再固定显示「46 条」）。 |
| BUG-04 | 中 | 新增 `build_model_compare_answer()`：未指明型号的保温类问题先追问并分别给出 BX-500(≥60℃)/BH-1000(≥65℃)；多型号对比时分别给出各型号参数及测试条件。 |
| BUG-05 | 中 | 启用开发 A 的 `knowledge_base.json`（219 条），并新增 `/admin` 索引管理页与 `POST /api/import`：可上传 PDF（PyMuPDF 解析）或 JSON（标准库解析）重建索引；展示主题页码、条目数与章节；失败给出明确原因（AC-F04-01~04）。 |
| BUG-06 | 低 | 前后端均增加 `MAX_QUESTION_LEN`（默认 500 字符）超长输入拦截，返回清晰提示。 |
| BUG-07 | 低 | 前端在空输入提交时同时清空上一次结果区，避免旧结果残留误导。 |

> 说明：检索内核从「阿里云百炼 RAG 云端语义检索」调整为「本地结构化索引规则检索」，原因是实测暴露出云端切片合并多个主题、QM 编号过载、top1 命中封面/目录页、前端泄露 OSS 路径，且无法提供本地索引管理界面。调整后每条结果可精确对应到单一主题、页码与资料版本，检索可离线复现，便于测试复核。
